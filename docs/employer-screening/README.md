## Flow and invariants

1. All application rollout gates default OFF, including separate notice-copy approval and public notice-display gates. OFF retains the existing application and employer notification path. ON uses a service-only atomic apply RPC after normal verified-seeker authorization; the RPC rechecks identities and active job, and persists the selected delivery path with the application. Failure or an uncertain commit never falls through to another insert or legacy email. Disabling new screening does not reroute already-selected outbox work.
2. Before insertion, capture the original uploaded PDF or render a bounded detached builder snapshot in a terminable worker. The private capture is preregistered for orphan cleanup, uploaded without overwrite, and named with applicant/application/version UUIDs. Exact bytes, size and SHA-256 bind attachment and extraction. Missing/invalid/unavailable capture still creates an ordinary application with no fabricated attachment metadata.
3. The database captures a separate immutable forwarding baseline from trusted applicant/job/company joins. It contains normal forwarding details and optional private attachment, not a required AI snapshot. Local document-quality material is a separate optional source-bound record, not a field inside the model/job-match snapshot. It can persist and be delivered when the job rubric is absent or the model fails. A job-specific rubric version is pinned at insertion when available. Approval is an authenticated employer-owner operation, checks verified/unbanned ownership again, uses version CAS, and permits only reviewed job criteria. Approval is not accepted from an applicant's `approved:true` flag.
4. Successful or unavailable enrichment finalizes the queue for immediate processing. If the request dies first, the absolute two-minute application cutoff makes the baseline eligible for a worker claim. `after()` kicks the worker after an accepted request; a separately approved scheduler/watchdog is still required for recovery during process failure. Eligibility is not an execution guarantee; see the [scheduler activation gates](scheduler-activation.md).
5. Screening is employer-only advisory evidence, with separate job-evidence and document-presentation reports. Missing evidence remains unknown. Failure of either optional report is unavailable, never a fabricated zero, and does not erase valid independent material or the forwarding baseline. No applicant status changes, hiding, ranking, automatic rejection, or late second score email occur. All-unknown assessments avoid a misleading `0/100` heading. The original forwarding email contains a compact advisory summary or an unavailable notice, plus the original captured CV when present.
6. Frozen email content, routing, attachment descriptor and nullable Reply-To are hashed before sending. Retries reuse that exact payload and `application/{applicationId}/employer`. Actual attachment bytes are verified again before dispatch. A changed owner/recipient or deleted application blocks new dispatch rather than rerouting private data.

## Uploaded PDF extraction and privacy

Exact-pinned Mozilla `pdfjs-dist` 6.4.299 runs locally in a disposable Node worker. It supports ordinary text PDFs, not OCR. Encrypted, damaged, scanned, oversized, excessive-page/text or unsupported documents return unavailable screening but do not remove the application/CV.

Limits: 5 MiB input, 20 pages, 30,000 decoded characters per page, 120,000 total characters, 20,000 text items, three-second parsing deadline and two concurrent parses per process. The worker has a bounded V8 heap, no inherited environment, no resource fetching, eval, font/image rendering, viewer scripts or annotation execution. Node worker heap limits are not an OS/native-memory/ArrayBuffer sandbox; runtime memory capacity and adversarial-load validation remain deployment responsibilities.

Capture-only reads enforce a shared absolute deadline and abort, admit at most 128 KiB per JSON response and 256 KiB across builder queries before SDK JSON parsing, select explicit fields and reject a collection beyond 50 rows rather than truncate it. Uploaded PDF responses are stream-capped at 5 MiB before Blob allocation. Normal admin clients and CV write routes are unchanged.

Builder input is bounded before cloning/rendering: at most 50 rows per collection, 150 total rows, 4,000 characters per field, 64,000 aggregate characters and 128 KiB serialized input. The existing template is serialized as allowed document primitives, not applicant-controlled code, then rendered in a separate worker with a three-second budget, 128 MiB V8 heap, 5 MiB output cap and two concurrent renders. Absolute capture deadlines are rechecked after each boundary and before writing. No image/font/network assets are accepted by that worker; its heap limit is not an OS/RSS sandbox.

Local extraction admits reviewed canonical skills/claims and bounded ordinary professional statements. Contextual evidence is an exact contiguous source record, not a rewritten or partially redacted quote. If the parser is unavailable, builder skills are not used as a context-free scoring fallback; the application and original CV still proceed. A closed reviewed professional/function-word vocabulary admits sentences rather than only stock phrases; unsupported identity/contact/protected/instruction records are omitted whole. Surrounding Summary/Notes and cross-page qualifiers are retained when admitted, with fixed derived cautions and generic omission markers otherwise. Raw decoded pages are transient local input, never a full-page provider fallback.

The provider receives positional IDs, categories, canonical concepts or admitted professional statements, bounded context, qualification cautions and derived source-order positions. No application/employer/source IDs, PDF bytes, hashes or page coordinates are sent. Limits are 50 evidence records, 20 context records, 400 characters per contextual record and 16,000 total retained characters, plus the existing provider byte/deadline limits. Unknown terms or optional omitted context do not mechanically invalidate every unrelated professional claim.

Canonical claims retain exact concept/category validation. For contextual claims, the model interprets the admitted narrative and surrounding context; deterministic code validates supplied citation IDs/category, rejects explicit negative/other-person/training/invalid-credential support and calculates weights. It does not claim deterministic semantic proof. All support is provisional, applicant-reported and unverified. Contextual interpretation is AI-assisted even though the compact employer email omits that visible label at the user’s request; it does not claim human review. Context records are never quoted as evidence, and fixed locally derived cautions are never presented as verbatim applicant statements. Credential criteria indicate at most reported attainment, never independently verified current validity or legal eligibility; employer verification is required.

Privacy filtering is risk reduction, not proof of complete de-identification or universal language understanding. Ordinary words can also be names; unfamiliar language, jargon and ambiguous extraction may reduce coverage. A source quote proves source presence, not truth or interpretation. Dates may remain local context; withholding raw dates is an engineering minimization choice, not a claim that employment dates are legally prohibited. No tenure, age, career-gap or licence-validity inference is made. See [context-privacy-review.md](context-privacy-review.md) for the expanded boundary, residual risks and mandatory separate approval. The earlier paid skills-only demonstration does not validate this new input or model semantics.

## Independent local document-quality assessment

`quality.ts` performs bounded deterministic document-presentation checks locally. It does not ask a model to judge arbitrary resume prose. Its four fixed 25-point dimensions concern recognizable organization, meaningful provided-entry identity/context, concrete task/evidence presentation and reliable linkage to that entry. They are independent of job criteria, model success and job-match totals. No candidate-merit, grammar/spelling, native-language polish, inferred visual design, organization-prestige, contact-disclosure, protected-trait or career-gap score is produced.

A report carries supported points, an observable denominator, unknown weight and coverage. For example, `50 / 50 observable points; 50 unknown; 50% coverage` is a partial document assessment, not an unqualified `100/100`. Missing work history or credentials are not failures. Unsupported fields stay unknown; only explicit supported issues such as an unfilled template marker can be flagged as needing attention. All-unknown and unreadable documents are not assigned a zero-quality label.

The implementation supports reviewed pipe/comma headers, bounded stacked title/context lines, concrete plain/bulleted statements and the actual JobLink builder's literal letter-spaced headings. It is still a finite local role/task grammar, not broad linguistic quality assessment. Unknown professional boundaries detach later evidence rather than falsely linking it to an earlier role. Tests include actual synthetic builder render → PDF extraction → quality paths, including multiple entries, not only injected labeled fixtures. See [quality-design.md](quality-design.md) for the precise rubric and limitations.

Quality reports contain fixed feedback codes and exact page spans. Optional excerpts are restricted to exact safe reviewed headings, labels, template markers and professional action/object prefixes. Unrestricted names and prose remain unquoted. Raw decoded pages remain transient and are neither persisted nor model input. Independent frozen quality is validated against the captured PDF hash, survives rubric/provider unavailability, and is included only in the original employer forwarding payload. Corrupt optional quality is discarded without changing the source CV or valid job report. It follows the same immutable retry, attachment-authority and deletion boundaries as the baseline.

## Compact original forwarding email

The new advisory block is a quick-scan summary, not a second email: job evidence points with unresolved weight, a separate supported presentation score out of 10 and at most two grounded presentation notes, at most two validated highlights and two actual verification prompts. The latest user clarification restores a concise score out of 10, not the old assessed-points breakdown. It uses supported points against the fixed whole rubric, never a partial observed denominator normalized to 10. Partial assessment is explicitly labeled; all-unknown or unavailable presentation is not assessed, never zero. The detailed observed denominator and unassessed point count remain private. The employer email labels job evidence unverified, without claiming human review. It does not display an AI-reviewed label at the user’s request; the separate applicant-facing notice still explicitly discloses AI processing. The order is presentation notes, Highlights, To verify, then Job match; a line break replaces the dash in the employer-notification footer. Local rule-based notes remain distinct from job evidence. Unknown credentials request evidence and never imply that the applicant claimed them. Missing/corrupt reports remain unavailable, not zero. Detailed structured reports stay private; no new public report link is created. The normal application header, contact details and conditional original-CV attachment wording remain intact. The generic recruitment tip is omitted only from the new advisory path.

Other users, apps, projects, API keys or manual calls outside this shared ledger are not covered. ## Durable delivery, reconciliation and cleanup

SQL uses row locks, `SKIP LOCKED`, fenced leases, immutable payload CAS, authoritative clock checks, four-attempt maximum and an original 23-hour send window (inside Resend's documented 24-hour idempotency retention). Poison rows are quarantined while later eligible work continues. No bulk sweep locks unrelated rows before claim.

Only definite pre-dispatch failure or documented rate-limit rejection can retry automatically. Timeouts, exceptions after dispatch, 5xx, missing acceptance and concurrent conflicts are uncertain, never blindly resent. Watchdog converts expired sending to uncertain. Signed Resend `email.sent`/`email.delivered` receipts bind application ID and payload digest and reconcile acceptance, including a receipt racing worker finish. A delivery webhook failure does not prove non-acceptance. Manual known-unsent reconciliation requires definitive provider evidence; an empty search or elapsed window is insufficient.

Deletion before dispatch cancels/redacts. Deletion after the dispatch linearization point cannot recall an external request; the tombstone retains minimal digest/receipt evidence and uncertainty. Captured objects are queued for exact-path cleanup, delayed at least 24 hours for in-flight uncertainty. Preregistered abandoned uploads become eligible after an hour, and live outbox references are excluded under locking. Cleanup has its own gate and does not require email credentials. No broad bucket deletion is used. The installed storage SDK has no per-upload signal option, so a capture-only bounded fetch links the actual upload to the shared abort/deadline. An aborted upload can still have an uncertain server-side outcome, which the preregistration journal covers. The hosting/storage lifetime must remain strictly below the one-hour orphan grace; late server completion and cleanup/apply locking require deployment and genuine PostgreSQL race tests.

The scoring cutoff prevents optional assessment from extending eligibility indefinitely; actual recovery still requires successful worker invocations and sustainable backlog. It is not a guarantee of network availability, provider acceptance or inbox delivery. Invalid recipient authority, database failure, storage corruption or provider outage cannot safely be bypassed with a direct send. Admin-only status exposes accepted/uncertain/blocked delivery without revealing the score, private payload, recipient or provider identifier; accepted means provider acknowledgement, not inbox delivery.
