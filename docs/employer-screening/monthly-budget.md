# Fixed US$5 monthly API boundary (unapplied launch preparation)

This is a separate delta after the frozen V4 review/publication source. It is not an activation, migration application, provider call, service purchase, credential setup or guarantee of a provider invoice. All runtime/database rollout gates remain OFF. The user's approval is US$5 per month for API usage only.

## Enforced scope and accounting

- Money is integer microUSD, rounded upward. The fixed cap is 5,000,000 microUSD. The private `budget_months` table has one allowed scope, `joblink-screening-api`, and a primary key on scope plus UTC first-of-month date. Its CHECK forbids negative balances and balances above the cap. Neither scope nor cap is accepted by an RPC or drawn from an employer/configuration account ID.
- Every reservation under every immutable rate/configuration version and every employer account shares this same ledger. `account_id` remains tenant/audit metadata, not a new allowance. Configuration changes do not reset the month. Existing per-application and per-configuration UTC-day restrictions remain additional constraints, never substitutes for the global month.
- The entire verified model input context plus all configured output/reasoning is reserved before dispatch. A request too expensive for the application/day/month is unavailable; no token ceiling reduction, model fallback, retry or extra paid request is used to fit it.
- Budget updates are transactional. Mutations lock reservation when present, then the global month row, then the configuration/day row. Operations requiring outbox identity lock outbox first; enabled configuration rows use shared locks before ledger locks. The authoritative UTC clock is sampled again after blocking ledger locks. Month/day rollover fails closed rather than silently transferring the old hold or borrowing a prior allowance.
- One reservation per application remains a uniqueness constraint. Repeating the same live reservation is idempotent. Dispatch is a one-time reserved-to-dispatched CAS. It requires current lease, deadline, tenant authority, enabled config, existing funded ledgers and the same current UTC day/month.
- At the cap, optional screening cannot reach the provider. The normal immutable application forwarding email, captured original CV when available, and independent local document observations can still proceed through the existing outbox. Budget failure never authorizes direct/duplicate sending or bypass of recipient, storage or delivery safety checks.

## Unknowns, releases and settlements

A hold is fully charged until bounded trusted usage proves a smaller token charge or the database proves dispatch never occurred. HTTP errors, timeouts, missing/malformed usage, invalid prices/usage ceilings, unexpected cache writes, interrupted settlement and uncertain start outcomes do not refund money. Full holds survive application deletion, config disabling and deployment changes.

`employer_screening_release_budget` is strictly pre-dispatch cancellation. It requires the original lease and `reserved` state with no dispatch timestamp, atomically refunds both original ledgers, and makes a terminal `released` state. Repeating it with that lease succeeds without another refund. A released application cannot re-reserve or dispatch. Dispatched, uncertain and settled requests cannot use this release RPC. The provider adapter only asks for release before a fetch attempt; if release is false/unknown, conservative settlement is attempted and the durable charge stays unless proved otherwise. A database start that succeeded but never reached fetch remains conservatively charged.

Usage settlement uses the reservation's immutable original rates, integer upward rounding, bounded input/output counts and a unique response evidence ID. An amount exceeding the original or currently charged reserve is refused and stays uncertain. Duplicate exact settlements are idempotent; conflicting repeats are refused. A duplicate receipt on a different reservation causes a transactional rollback, so neither ledger receives a partial refund. Settlement can move uncertain to settled when valid evidence arrives. Any reduction affects the original reservation UTC month/day, including after a calendar boundary; it never creates credit in the current month. There is no general operator/provider-refund or credit rollover API in this delta.

## Boundary that this cannot enforce

The month is the database's UTC dispatch-authorization month, not the provider's independent billing calendar. Dispatch authorization, transaction commit, outbound networking, execution and billing attribution are not one atomic event. A request authorized before midnight can be billed after midnight. Existing per-day and new per-month terms must acknowledge this precise definition before activation.

This bounds the reviewed app path only, assuming the pinned full-context/output bounds and approved rate schedule cover the provider's actual maximum billable usage and any relevant charges. It does not meter another app, manual calls, other projects/API keys, or already-incurred usage absent from this database. Database owners can change schema or history, and credentials used outside this worker can bypass it. A literal provider-account invoice hard cap needs independently verified provider controls and a suitably exclusive/shared-account consumption policy. No such account settings, credentials, persistence grants or external usage were inspected or changed here.

Keep history in the same persistent database across deployments. Do not deploy parallel independent copies of this scope, truncate/reset balances, discard unknown holds, restore an old backup over newer reservations, or switch accounts/config IDs to evade the approved bound. Reconcile prelaunch same-scope usage and any restoration gap conservatively. Pricing/context validation, external billing controls if required, privacy, scheduler, retention and delivery approval remain activation gates. A US$5 API allowance is not approval to buy hosting, email service, cron infrastructure or credentials.

## Fresh install versus V4 upgrade

Fresh synthetic installs use `drafts/employer-outbox.unapplied.sql`, never both drafts. V4-installed synthetic databases use `drafts/employer-monthly-budget-upgrade.unapplied.sql` after separately authorized migration review and rollback rehearsal. These are review files outside the migration runner, not generated/applied production migrations.

Upgrade preconditions:

1. Preserve a backup and reconcile historical provider usage without discarding reservation evidence. Stop/drain paid workers; do not send baseline mail through a second path. Every database budget configuration must already be disabled. The upgrade checks this and fails otherwise; it does not change live gates for the operator.
2. The upgrade takes exclusive locks on V4 outbox/configuration/reservation/day tables in one transaction, creates the global month ledger, and backfills every historical reservation state and configuration/account. It sums existing charged amounts by their original UTC reservation day/month. V4 unknown/dispatched/reserved holds retain their full existing amount; settled amounts stay settled.
3. Historical months above US$5 or invalid reservation bounds abort the entire transaction, leaving V4 unchanged. Do not reset history or raise the cap to force installation. Keep paid workers disabled and obtain a reviewed reconciliation/activation plan. Older out-of-scope provider calls cannot be discovered by this SQL and must be separately reconciled.
4. All reserve/start/settle functions are replaced atomically with the fresh-install definitions, and the release RPC gets service-role-only permission in the same commit. The mandatory reservation month has deliberately no default: an already planned legacy reserve function using the old insert shape cannot create an unmetered new reservation after upgrade. Any failure rolls back all schema/data/function changes.
5. Validate new private-table RLS/grants, current Supabase advisors, exact function definitions, ledger sums, synthetic real-PostgreSQL races and rollback behavior before enabling separately approved gates. Never roll the budget functions back to V4 while paid work can run. On rollback, keep paid work OFF and preserve monthly/reservation evidence; do not drop the ledger or reactivate older routines.

Current Supabase changelog and RLS guidance were checked for this design. The reviewed changelog's upcoming legacy TLS-cipher removal is not a change to these PostgreSQL row-lock/transaction primitives. No hosted advisors or deployment tests were run. Relevant primary references: [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html), [Supabase RLS and grants](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase changelog](https://supabase.com/changelog).

## Verification and honest limits

Dedicated PGlite tests cover fresh default-OFF schema, fixed scope/cap, cross-configuration and employer IDs, exact/full-context limits, idempotency, unknown/invalid/duplicate settlement, original-month refunds, cancellation, UTC rollover, permissions, no-provider/baseline fallback, V4 backfill/definition parity, active-config refusal and over-cap rollback. Provider adapter tests use only injected synthetic responses.

The real PostgreSQL suite adds eight cases: shared last-slot race across configs/employers; both dispatch/release orderings; both settlement/reserve orderings; independent month accounting; dispatch/reserve month rollover after demonstrable lock waits. Its deterministic clock shim exists only inside the disposable fixture database and restores the exact production function definitions. It does not add a production clock parameter or weaken production timing.

Without `OUTBOX_TEST_DATABASE_URL`, all genuine PostgreSQL tests explicitly skip. Only an existing empty localhost database named `joblink_outbox_test` is accepted. PGlite serializes execution and is not proof of independent-session races. Final exact-source verification counts and artifacts are reported separately; independent external review, genuine PostgreSQL execution, hosted permissions/advisors and rollout prerequisites remain pending.
