# Sol résumé review v2 (default OFF)

This source-only upgrade enriches the original `forwardApplicationToEmployer` email. It does not introduce another queue, public test endpoint, application, attachment, email, retry, or credential. The original `application/{id}/employer` key and original attachment bytes are unchanged. The existing 25-second absolute enrichment deadline includes parsing, job read, count admission, token counting, reservation, inference and validation. The PDF worker retains its 3-second limit. Deadline/failure sends the original application email; a process/host crash remains an existing delivery limitation, not something this hook can solve.

## What the employer sees

Two whole-number document ratings: **Résumé quality** and **Résumé fit for this role**, a short role-specific critique, at most two highlights and two gaps/verification questions. Six fixed 0–4 dimensions are grouped three per rating and deterministically rounded to an integer out of10. No partial denominator is normalized into10/10. Partial/insufficient professional input, incomplete job context or an unknown dimension withholds the affected rating. Missing evidence concerns the submitted document, not the applicant's ability. Ratings are subjective structured model judgments aggregated by code, not validated psychometrics or hiring recommendations.

The model reads admitted professional records and published duty/required/preferred clauses in source order; it prioritizes useful findings rather than mechanically returning every job clause. It cannot reject, rank, hide or select applicants. Output validation enforces schema, bounds, cited-ID membership, fixed dimensions, uncertainty gates and prohibited-text defenses. Citation membership proves provenance linkage, not semantic entailment, truth, credential validity or comprehensive safety. Only employers receive the summary; the applicant-facing linked Terms disclosure explicitly describes OpenAI/AI processing and document critique.

## Professional input boundary

`professional-projection.ts` is separate from the old finite-vocabulary evidence extractor. It admits bounded professional sections, including ordinary roles, employers, employment dates, duties, achievements, skills and qualifications. Original heading semantics, qualifiers, negation, third-party attribution and source order survive; exact page/UTF16 spans and PDF SHA remain local. Provider records contain opaque IDs, section, order and admitted text, not attachment bytes, identity fields, source digests or storage paths.

Identity/contact/private/protected disclosures and instruction-like content are screened locally. Whole unsafe scopes are omitted, not redacted into misleading positive fragments; omitted global qualifying context can quarantine the remaining projection. Intended header removal does not itself lower coverage. Unknown professional sections and limits remain explicit. This pattern-based risk reduction is **not an anonymization guarantee**; indirect/novel disclosures and semantic prompt injection remain residual risks. No OCR, visual-layout evaluation or independent factual verification is claimed. Review the exact boundary and synthetic cases before approval; do not silently substitute raw PDF/page fallback.

## Request and spending controls

- Model pinned to `gpt-6.1-sol`, reasoning `low`, output maximum2048, default/Standard service tier, no tools, files, conversation, background, streaming or storage.
- Explicit cache mode with no breakpoints. Unexpected tier, model, token overflow, cache-write or missing accounting is uncertain, not zero cost.
- One permanent service-only per-application claim occurs **before** counting. It checks ownership/path/status/configuration, existing attempts and conservative full-request month/day headroom. Its nonce/source/config/request proof prevents repeat counting or a Luna/other-path replay. Failure burns that application's attempt; no reset or sweeper.
- The exact generation JSON is frozen and SHA-bound. All token-bearing model/instructions/input/reasoning/tool/schema fields are identical in `/responses/input_tokens` and `/responses`; generation-only controls are excluded from count. Counts outside1–16000 reject without generation, not truncation.
- A second atomic service-only RPC reserves exact count plus2048 output against the existing fixed `joblink-screening-api` UTC-month row and existing day ledger. All model/config versions share the unchanged $5 monthly ceiling and application uniqueness.
- Conservative configured rates are5,500,000 input and16,500,000 output microUSD per million tokens (include long-context/cache-write/regional margin even though the request disables cache writes). Maximum generation hold is121,792 microUSD ($0.121792). Known usage settles at the configured conservative rates, not an assertion of invoice cost. Unknown inference/settlement retains the full hold. Early full-bound admission can leave the last less-than$0.121792 unavailable.
- Claim and dispatch cutoffs survive lock waits, with synchronous final fences immediately before native count/generation fetch. RPCs have function-local one-second lock waits. No automatic HTTP retry or alternate model.

Official references: [token counting](https://developers.openai.com/api/docs/guides/token-counting), [per-run spending controller](https://developers.openai.com/cookbook/articles/per_run_spending_controller_responses_api), [model](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching). The controller pattern is count then exact reserve, preceded here by bounded admission. We do not assert that the count endpoint is free where no explicit commercial guarantee is published. The ledger models screening generation dispatch; it does not cap unrelated activity using the account/key or hosting charges. A newly identified billable count category requires accounting review before activation.

### Shutdown / rollback

Disable the Sol budget configuration first: new attempts fail closed to ordinary application forwarding. Do not delete proof/history or refund uncertain calls. The v2 flag may remain true while paused (baseline-only). A deliberate rollback to Luna requires both setting the v2 flag false and re-enabling the previously reviewed Luna configuration; do not automatically fall back after any count or Sol attempt. Additive columns/functions can remain inert. Do not drop tables/history as rollback.
