## Customer and human fulfillment flow

1. Review the optional package and approved terms. Sign in or create/verify an existing JobLink seeker account. A canonical return path preserves only an opaque order ID and validated application destination; no questionnaire data travels in URLs.
2. Explicit consent creates a private draft. Save incomplete fields, including an unfinished email; resume later from saved requests or its owner-authorized URL. Submit validates contact details, target job and experience choice, then freezes the questionnaire. Unsaved form changes stay in memory. The existing builder remains mounted and keeps its own unsaved edits.
3. Checkout uses the selected server policy and only an opaque `client_reference_id`. Stripe opens in a new tab. A browser return never marks payment paid. Payment can precede questionnaire completion: a paid draft waits in `awaiting_intake` until explicitly submitted.
4. A verified payment plus completed questionnaire enters the admin work queue. Admin starts writing, prepares documents manually, and uploads a PDF plus editable DOCX (each at most 3 MiB). The 3 MiB bound plus multipart overhead stays below the host’s [4.5 MB request/response cap](https://vercel.com/docs/functions/limitations#request-body-size). Files are staged privately and never overwrite an existing object. Retry uses the same upload ID and verifies identical bytes.
5. Admin downloads both files, checks the current questionnaire/revision note, and explicitly confirms human review. Publication verifies private storage, file hashes, current revision, payment, actor and optimistic order version, then atomically publishes exactly that pair.
6. The verified owner downloads through an authenticated private/no-store attachment route. Owner/policy, publication, current revision and fresh authoritative payment state are required. Object paths and permanent public URLs are never exposed. Admin can download staged files only through the admin-checked review path.
7. The owner can approve a draft or request the included revision with a bounded note. A locked transaction permits one revision, with idempotent request retry. Admin writes and publishes a new reviewed pair for round 1. Approval marks completion; approval alone does not silently waive an unused revision. The final approved revision window remains a launch gate.

The order tracks payment, questionnaire and fulfillment independently. Duplicate payments, any refund (including partial), or dispute cause a sticky review hold without erasing fulfillment progress. Manual reconciliation discovers missing receipts and unmatched events; it never matches by applicant email. Hold resolution/refunds remain an explicitly approved operator action outside this feature. There is no automatic customer email: customers return to their saved request page to check status and download.

## Payment verification and isolation

The dedicated résumé Stripe client cannot fall back to employer credentials. Mode/account/link/product/price/currency/amount/quantity, successful payment intent and captured charge are retrieved from Stripe and checked. Event, receipt and order updates share one transaction; receipt uniqueness and sticky holds protect duplicate/out-of-order recovery. Signed résumé events cannot enter employer entitlements. Checkout being paused does not disable reconciliation.

The existing `/api/webhooks/stripe` accepts a separate selected résumé signing secret and preserves existing employer verification. Do not replace the employer secret or remove its event subscriptions.
